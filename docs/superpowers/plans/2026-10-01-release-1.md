# Kanban Lite Release 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Deliver a persistent multi-repository localhost board with verification-aware completion, CI, Dependabot, and live README badges.

**Architecture:** A Node.js loopback service owns SQLite writes. A framework-free browser UI uses authenticated same-origin HTTP operations. Domain interfaces are designed for the later MCP adapter, which is outside this release.

**Tech Stack:** Node.js 24.x, TypeScript, built-in HTTP/SQLite/test APIs, npm, ESLint, Playwright. Pin the exact supported Node patch and dependency versions in configuration and lockfile during Task 1; start from locally verified Node 24.21.0 and verify its official API behavior. Do not rely on APIs introduced only in Node 25.

**Spec:** `docs/superpowers/specs/2026-10-01-kanban-lite-design.md`

## Global Constraints

- Preserve all three product priorities: lightweight operation, shared Claude Code/Codex support, and compatibility with Agent Skills, Superpowers, and OpenSpec. Release 1 establishes the foundation; it does not claim completed host or workflow integration.
- No Docker, external database, hosted service, or model API is required. Keep the browser framework-free and idle operation free of repository scanning or agent polling. Justify each runtime dependency.
- The service binds to 127.0.0.1.
- The local service is the sole database writer.
- Repository registration is explicit; paths are canonicalized and file reads are confined to registered roots.
- OpenSpec files remain authoritative for specification and task content; the database owns Kanban position, ownership, priorities, and history.
- Every mutation supplies the expected revision.
- Columns are Backlog, Ready, In Progress, Review, and Done.
- Blocked is a flag with a reason, not a separate workflow stage.
- Kanban column and SDLC phase are separate fields.
- Cards cannot enter Done without recorded passing verification evidence, or an explicit human override with a reason recorded in history.
- MCP clients cannot submit human overrides.
- No OpenSpec parser, plugin packaging, cloud hosting, automatic command execution, or paid model calls in this release.
- Preserve normal prose in code, documentation, and commit messages.

## Review Focus

1. Paths with spaces, symlinks, and repeated registrations must resolve consistently without duplicate projects or escaping registered roots (Task 2).
2. Two browser tabs editing the same card must produce a visible conflict, not silently overwrite data (Tasks 3 and 5).
3. Passed evidence followed by material card edits must not silently authorize completion of changed work (Task 3).
4. A hostile website or malformed request targeting localhost must not mutate state or expose local credentials (Task 4).
5. Interrupted migrations and occupied ports must fail clearly without losing existing data or starting a second writer (Tasks 1 and 6).

## File and interface map

- `src/config.ts`: runtime validation, user data directory, port and credential configuration.
- `src/storage/database.ts`, `migrations.ts`, `backup.ts`: database lifecycle, transactional schema, safe backup.
- `src/domain/types.ts`, `projects.ts`, `cards.ts`, `evidence.ts`, `events.ts`: shared operations and validation.
- `src/security/paths.ts`, `session.ts`: canonical containment and browser sessions.
- `src/http/server.ts`, `routes.ts`, `errors.ts`: loopback transport, bounded requests, structured errors.
- `src/cli.ts`: explicit startup and backup commands.
- `public/index.html`, `styles.css`, `app.js`, `api.js`: board and accessible controls.
- `tests/storage/`, `tests/domain/`, `tests/http/`, `tests/browser/`: behavior-oriented verification.
- `package.json`, `package-lock.json`, `tsconfig.json`, `eslint.config.js`, `.node-version`, `.gitignore`, `playwright.config.ts`: reproducible tooling.
- `.github/workflows/ci.yml`, `.github/dependabot.yml`, `README.md`: automation and usable documentation.

All domain functions consume `Store` (database handle) and return promises or synchronous typed results consistently: domain CRUD is synchronous; filesystem registration and backup are asynchronous. HTTP converts domain errors into status codes.

Types: `Column` is the five exact column names; `Phase` is Discovery, Design, Planning, Implementation, Review, or Verification. `Actor` contains `client: 'browser' | 'claude' | 'codex'` and `humanSession: boolean`, assigned by the transport rather than request bodies. IDs are UUIDs; revisions are positive integers. `ConflictError` includes current entity; `ValidationError`, `NotFoundError`, and `PolicyError` are distinct error classes.

## Task 2: Safe multi-repository registration

**Files:** `src/domain/types.ts`; `src/domain/projects.ts`; `src/security/paths.ts`; `tests/domain/projects.test.ts`.

**Interfaces:** `registerProject(store: Store, input: {name: string; root: string}, actor: Actor): Promise<Project>`; `listProjects(store: Store): Project[]`; `updateProject(store: Store, id: string, expectedRevision: number, patch: {name?: string; wipLimit?: number}, actor: Actor): Project`; `resolveProjectFile(root: string, relativePath: string): Promise<string>`.

Registration uses expected revision 0 to mean create-if-absent; existing canonical roots return the existing project without overwriting settings. Project updates require current positive revision. WIP limits are positive integers or absent.

## Task 3: Cards, conflicts, history, and verification

**Files:** `src/domain/cards.ts`; `evidence.ts`; `events.ts`; `tests/domain/cards.test.ts`.

**Interfaces:** `createCard(store, input: NewCard, expectedRevision: 0, actor): Card`; `getCard(store, id): Card`; `listCards(store, projectId?: string): Card[]`; `updateCard(store, id, expectedRevision, patch: CardPatch, actor): Card`; `moveCard(store, id, expectedRevision, column: Column, actor, overrideReason?: string): {card: Card; warnings: string[]}`; `recordEvidence(store, cardId, expectedRevision, input: EvidenceInput, actor): Card`; `listEvents(store, cardId): Event[]`; `deleteCard(store, id, expectedRevision, actor): void`.

Card includes priority (low/normal/high/urgent), nullable owner, blocked reason, phase, revision, workRevision, timestamps, and artifact metadata. Material changes to title, description, or artifacts increment workRevision. Evidence records its workRevision and outcome (passed/failed). Only passed evidence matching current workRevision qualifies; a later failure for that workRevision supersedes earlier success. Moving columns, ownership, and priority do not invalidate evidence. Deletion is soft deletion with an event. Events record actor and before/after revisions in the same transaction.

- [ ] Write tests for CRUD, project isolation, exact columns, nonblank titles, stale revisions, event atomicity, soft deletion, WIP warnings, missing verification, material edits invalidating evidence, failure superseding success, and browser-only overrides with nonblank reasons. Assert a failed write changes neither entity nor history.
- [ ] Run `npm test -- --test-name-pattern='card|evidence|override|WIP'`; verify tests are discovered and fail for missing behavior.
- [ ] Implement interfaces, input bounds, conflict payloads, current-work evidence policy, and transactional history. Bound titles to 200 characters, descriptions to 20000, reasons to 2000, and evidence summaries to 4000. Do not execute checks; evidence is recorded with attribution.
- [ ] Rerun targeted tests and typecheck; expect pass.
- [ ] Commit domain operations.

## Task 4: Authenticated localhost service

**Files:** `src/security/session.ts`; `src/http/server.ts`; `routes.ts`; `errors.ts`; `tests/http/server.test.ts`.

**Interfaces:** `startServer(store: Store, config: Config): Promise<{url: string; close(): Promise<void>}>`. REST endpoints: GET `/health`, `/api/projects`, `/api/cards?projectId=...`, `/api/cards/:id/events`; POST `/api/projects`, `/api/cards`, `/api/cards/:id/evidence`; PATCH `/api/projects/:id`, `/api/cards/:id`; POST `/api/cards/:id/move`; DELETE `/api/cards/:id`. Mutation bodies contain expectedRevision; DELETE uses an expectedRevision query parameter. Domain signatures define payloads.

- [ ] Write HTTP tests for unauthenticated access, hostile Origin/Host, missing CSRF, forged humanSession, oversized/malformed JSON, unknown endpoints, revision conflict, valid create/list/move, and occupied-port startup. Expect 401, 403, 413, 400, 404, and 409 as applicable, without stack traces or credentials in responses.
- [ ] Run `npm test -- --test-name-pattern='HTTP|session|occupiedPort'`; expect missing behavior failures.
- [ ] Implement loopback-only server, exact Host/Origin validation, same-origin static assets, no permissive CORS, CSP, 64 KiB body limit, JSON schema validation, and structured error responses. Serve no arbitrary filesystem paths.
- [ ] Implement one-time browser bootstrap credential in URL fragment, exchanged by a same-origin POST for HttpOnly SameSite=Strict session cookie and CSRF token. Remove fragment immediately; never log credentials. Keep long-lived service credential in a mode-0600 file; do not accept it from URL query strings. Browser override requires session-derived humanSession and explicit UI confirmation; this is an interactive-session distinction, not proof of human identity.
- [ ] Rerun HTTP and domain tests; expect pass.
- [ ] Commit local service.

## Task 6: Startup, backup, and recovery

**Files:** `src/cli.ts`; `src/storage/backup.ts`; `tests/storage/backup.test.ts`; `tests/http/cli.test.ts`.

**Interfaces:** CLI `kanban-lite start [--port N] [--data-dir PATH]`; `kanban-lite backup --output PATH [--data-dir PATH]`; `kanban-lite restore --input PATH [--data-dir PATH]`. Backup/restore use the live service when running; offline mode acquires the same exclusive data-directory lock as startup. `backupStore(store, destination): Promise<void>` refuses existing output files.

- [ ] Write tests for restart persistence, recoverable backup with history/evidence, refusal to overwrite backups, invalid restore, refusing restore while service runs, and cleanup of failed startup locks. Assert restore leaves the current database untouched on validation failure.
- [ ] Run targeted backup/CLI tests; expect missing behavior failures.
- [ ] Implement exclusive service lock with PID/liveness checks, signal cleanup, actionable startup errors, and consistent SQLite backup. Restore only while stopped; validate schema/integrity, preserve pre-restore backup, and replace atomically. Print the board URL without credentials and offer an explicit `--open` browser launch using a platform-native argument-safe invocation.
- [ ] Rerun tests and manually restart with a temporary data directory; expect preserved cards.
- [ ] Commit operational commands.
